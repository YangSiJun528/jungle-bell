# Codex 메인 에이전트 작업 안내

> 문서 유형: 방법 안내(how-to guide)

메인이 구현·수정 작업을 시작할 때 읽는 전용 안내입니다.
하위 담당자에게는 작업의 목표·범위·완료 조건과 필요한 진단·검증만 전달하며,
이 안내 전체를 읽도록 요구하지 않습니다. 역할 설정과 공통 협업 절차는
[하네스 사용 안내](guide-codex-harness.md)를 참고합니다.

## 요구사항과 완료 조건 확인

메인은 구현·수정 작업을 시작할 때 목적·범위·완료 조건을 파악하고, 완료 조건을
테스트·검사 명령 또는 관찰 가능한 결과와 연결합니다. 해석에 따라 결과가 크게 달라지는
부분은 구현 전에 사용자에게 권장안과 대안의 차이를 짧게 제시해 질문합니다.
코드·문서에서 확인할 정보는 직접 조사하고, 사용자만 정할 수 있는 요구사항은 먼저 묻습니다.
영향이 작고 되돌리기 쉬운 선택은 가정을 밝히고 진행하며, 이미 합의한 조건은 다시 묻지 않습니다.

## 수정 담당자 선택

메인은 조사·작업 분해·위임·결과 통합·검증 관리를 맡고, 전문 역할의 담당 범위에 속하는 구현·수정은 위임합니다.
Frontend·Desktop·Server 작업은 각각 `jb_frontend`·`jb_desktop`·`jb_server`에 맡깁니다.

이 범위에서 메인이 직접 수정할 수 있는 예외는 의미·로직·동작·계약·설정·산출 결과를 바꾸지 않는
문서·주석의 단순 오타·서식 수정뿐입니다. 줄 수·파일 수·예상 작업 시간은 예외의 기준이 아닙니다.
한 줄이어도 계산식·조건문, 사용자에게 표시되는 값·산출 결과 또는 검증·완료 판정 규칙을 바꾸면
위임합니다. 직접 구현한 뒤 독립 검토만 받는 것으로 구현 위임을 대신하지 않습니다.

## 작업별 검증과 완료 판정

작업을 나눌 때 각 작업의 완료 조건·검증 방법·담당자를 함께 정합니다. 작업 단위는 결과를
독립적으로 확인할 수 있는 변경 묶음으로 잡고, 연관된 소규모 변경은 함께 검증합니다.
검증 범위는 변경과 직접 영향을 받는 동작에 맞추며, 기존 검사와 실행 증거를 우선 활용합니다.

1. **구현 담당자의 자체 검증:** 완료 조건별로 예상 결과와 실제 결과를 대조합니다.
   버그 수정은 가능한 경우 수정 전 실패와 수정 후 통과를 같은 재현 방법으로 확인합니다.
   테스트 파일의 존재나 구현자의 완료 선언만으로 조건을 통과시키지 않습니다.
2. **최종 조합·QA 결과 수집:** 여러 담당자나 영역의 결과를 연결한 뒤 생산자·소비자 계약과 대표 흐름을
   확인합니다. 필요한 실제 화면·OS 동작은 `jb_visual_qa`에 맡깁니다. 전체 기능 QA는 기존 릴리스
   기준을 따릅니다. 서로 독립적인 구현·검증·QA는 병렬로 진행할 수 있습니다.
3. **최종 독립 검토:** 동작·계약·상태·실행 설정 또는 검증·완료 판정 규칙이 바뀌면 구현에 참여하지
   않은 `jb_reviewer`가 검토합니다. 메인은 자체 검증과 필요한 조합 확인·QA 결과를 모두 받은 뒤
   해당 결과와 변경을 함께 전달해 최종 검토를 요청합니다. 동작이나 규칙을 바꾸지 않는 문서 수정은
   문서 검사로 충분하며, 동작을 규정하는 명세나 에이전트 지침 변경은 독립 검토 대상입니다.
4. **수정과 판정 갱신:** 근거 있는 지적은 편집 담당자가 수정하고 해당 조건을 재검증합니다.
   메인은 같은 Reviewer에게 `followup_task`로 변경과 갱신된 근거를 전달하고 새 판정을 받습니다.
   비결함으로 판단할 때도 원래 요구사항·코드·실행 근거를 남깁니다. 의견이 다르면 메인이 근거를
   대조하며, 확인되지 않은 필수 조건은 미검증으로 남깁니다.

독립 검토가 필요한 작업은 최종 Reviewer의 결과를 받은 뒤 완료 여부를 판단합니다.
리뷰 뒤 코드나 판정에 영향을 주는 검증 결과가 바뀌거나 뒤늦은 결과가 도착하면, 같은 Reviewer에게
`followup_task`로 재검토를 요청하고 갱신된 판정을 기다립니다. 이미 종료한 Reviewer에게 `send_message`만
보낸 상태를 검토 완료로 처리하지 않습니다.

Reviewer에게는 [검토 인계 템플릿](template-codex-review.md)의 원래 요구사항·제약·완료 조건,
대상 파일·diff, 실행한 명령·실제 결과·증거 경로, 미검증·남은 문제를 함께 전달합니다.
작은 작업은 같은 정보를 한 메시지에 담아도 되며, 파일 작성은 필수가 아닙니다.
새 Reviewer는 `fork_turns="none"`으로 시작하고, 구현자의 추론 대화나 성공 주장에 기대지 않고
요구사항과 변경을 직접 대조하게 합니다. 확인 가능한 기존 실행 증거는 재사용하고, 부족한
부분만 추가 검사합니다. 결함 개수나 반대 의견을 할당하지 않습니다.

파일이 필요하면 저장소 루트에서 아래처럼 빈 템플릿을 저장소 밖에 복사합니다.
실행 상태·인계 보고서·로그·캡처는 대화나 저장소 밖에 두고 커밋하지 않습니다.

```bash
review_handoff_dir="$(mktemp -d /tmp/jungle-bell-review.XXXXXX)"
cp docs/template-codex-review.md "$review_handoff_dir/review.md"
```

코드 검토에서 결함을 찾지 못한 결과와 실행 검증 결과는 구분합니다.
요구사항을 충족한 근거가 있으면 **통과**, 충족하지 못한 사실이 확인되면 **실패**입니다.
환경·인증 부족, 검사 미실행 또는 근거 부족으로 판단할 수 없으면 **미검증**으로 남기고 이유를
적습니다. 필수 조건의 실패·미검증이나 해결되지 않은 결함이 남으면 해당 작업과 전체 목표를
완료로 보고하지 않습니다. 독립적인 작업은 계속하고, 필요한 준비와 남은 범위를 사용자에게 알립니다.

테스트 삭제·assertion 완화·skip 추가나 완료 조건 축소를 통과의 근거로 삼지 않습니다.
요구사항 변경에 따른 검사 수정은 변경 이유와 검증 범위의 적절성을 독립적으로 확인합니다.
재검증 중 진전이 없으면 아래 반복 실패 대응을 따릅니다. 모든 에이전트의 동의를 얻기 위한
무한 반복이나 실행 증거가 같은 전체 검사 반복은 요구하지 않습니다.

## 검증 규칙을 바꿀 때

지침·역할 설정을 바꾸면 문법·경로 검사에 더해 작은 행동 검증을 수행합니다. 저장소 밖에
정상 사례, 알려진 결함이 있는 사례, 필수 검사를 실행하지 못한 사례를 준비하고 기대 판정을
미리 기록합니다. 검증자에게는 요구사항·산출물·실행 증거를 주고 기대 판정은 주지 않습니다.
결함 누락·정상 사례의 오탐·미검증을 통과시키는지를 확인합니다. 한 번의 성공을 일반적인
탐지율로 보고하지 않으며, 문제가 생기면 실제 실패 사례를 다음 점검에 활용합니다.

## 반복 실패 대응

직접 작업하거나 담당자의 실패 보고를 받았을 때, 예상하지 못한 실패로 진행이 막혔다면
원인 가설과 최소 실험을 정합니다. 새 근거 없이 같은 수정·명령·위임을 반복하지 않습니다.
같은 문제에 같은 접근으로 2회 연속 새 증거나 원인 후보의 축소가 없으면, 기존 역할·작업 범위
안에서 가설·재현 방법·도구 등 접근을 바꿉니다. 명령 실패 횟수가 아니라 진전 없는 시도를 세며,
담당자를 바꿔도 같은 접근의 시도는 이어서 셉니다.

접근을 바꿔도 진전이 없고 검증할 다른 경로가 없으면 해당 경로를 중단하고, 시도한 내용·확인된
사실·막힌 이유·권장 다음 단계를 정리합니다. 사용자 결정·인증·권한·외부 준비가 필요한 막힘은
재시도 횟수를 채우지 않고 바로 질문합니다. 막힌 부분과 독립적인 작업은 계속합니다.
